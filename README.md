# PlannerWeb

Веб-версия Planer: **.NET 10, ASP.NET Core MVC, Razor, SQLite**. Ветка `master`.

Недельная раскладка 5+2, цвета, исходные PNG и Helvetica Neue перенесены из десктопного приложения. В составе есть месяц, год с тремя режимами, текущий день, привычки с сериями, повторяющиеся задачи и платежи, цели, заметки, матрица и текущий финансовый план. Карточки перетаскиваются целиком; редактирование/удаление доступны по ПКМ, клавишам F2/Delete. В меню задачи также есть перенос с клавиатуры.

Регистрация запрашивает никнейм, почту, пароль и подтверждение. Для входа подходит почта либо никнейм. Пароли хешируются стандартным `PasswordHasher` ASP.NET Core Identity; вход блокируется на 15 минут после пяти ошибок. Подтверждение почты, восстановление пароля, внешние провайдеры и роли не добавлены.

## Локальный запуск

Нужен .NET SDK 10. Никаких Windows SDK или Node.js для работы приложения не требуется.

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Development'
$env:Planner__DataDirectory = "$PWD/data"
dotnet run --project src/PlannerWeb --urls http://127.0.0.1:5080
```

Откройте `http://127.0.0.1:5080`. Создайте собственный аккаунт; демонстрационных аккаунтов и паролей в рабочей базе нет. По умолчанию данные хранятся в `data/planner-web.db`, ключи cookies — в `data/keys`. Эти каталоги исключены из Git и Docker context. В Production cookies требуют HTTPS; локальный HTTP используйте только с Development.

```sh
docker build -t planner-web .
docker run --rm -p 8080:8080 -v planner-data:/data -e ASPNETCORE_ENVIRONMENT=Development planner-web
```

Последняя команда предназначена для локальной проверки по HTTP. На хостинге оставьте `Production` и HTTPS.

## Amvera

Готовые `Dockerfile` и `amvera.yml` лежат в корне. Контейнер слушает **0.0.0.0:8080**, постоянное хранилище монтируется в **/data**. При старте entrypoint настраивает права смонтированного тома, затем запускает .NET от непривилегированного пользователя `app`.

1. Создайте приложение в Amvera и подключите публичный GitHub-репозиторий, ветку `master`, либо отправьте эту ветку в Git Amvera по инструкции хостинга.
2. Используйте Dockerfile из корня; `amvera.yml` задаёт порт 8080 и `/data`.
3. Включите HTTPS для выданного домена. В переменных задайте `AllowedHosts` равным вашему домену (несколько доменов разделяются `;`). Не указывайте схему и путь.
4. Оставьте **одну реплику**. SQLite и блокировка полного цикла чтение–изменение–запись рассчитаны на один процесс. При развёртывании используйте остановку старой реплики перед запуском новой; не допускайте перекрытия двух версий с одним томом.
5. Для проб доступен `GET /health` (200 при доступности SQLite). После первого запуска зарегистрируйтесь и проверьте сохранение записи после перезапуска.

Переменные (Docker уже задаёт значения по умолчанию):

| Переменная | Значение |
|---|---|
| `ASPNETCORE_ENVIRONMENT` | `Production` |
| `ASPNETCORE_HTTP_PORTS` | `8080` |
| `Planner__DataDirectory` | `/data` |
| `Planner__ExternalHttps` | `true` — внешний HTTPS на ingress Amvera |
| `Planner__TimeZone` | `Asia/Yekaterinburg` |
| `AllowedHosts` | Домен приложения, например `planner-example.amvera.io` |

Путь БД — `/data/planner-web.db`; ключи авторизации — `/data/keys`. Сохраняйте оба при обновлении/резервном копировании, с ограниченным доступом. Потеря ключей завершит действующие сессии. Не загружайте данные или ключи в GitHub. База и ключи находятся на постоянном томе, исходники и бинарники — в `/app`. Для согласованной резервной копии остановите приложение и скопируйте постоянное хранилище через интерфейс Amvera. Во время работы нельзя копировать только файл SQLite без корректного online backup.

TLS завершается на ingress Amvera. Docker явно задаёт `Planner__ExternalHttps=true`: в Production приложение использует схему HTTPS для внутреннего HTTP-запроса от ingress, включая выпуск защищённого antiforgery token. Этот режим требует внешнего HTTPS и недоступности внутреннего порта напрямую из интернета. В Development он выключен. Приложение не доверяет произвольным `X-Forwarded-*` и не выполняет повторный HTTPS redirect, поэтому не создаёт циклы перенаправлений. Secure cookies включены независимо от внутренних HTTP-запросов. Ограничение частоты регистрации/входа действует по адресу непосредственного клиента Kestrel; за общим ingress это может быть общий лимит 20 запросов в минуту. Блокировка пяти ошибок дополнительно действует на аккаунт.

Основание конфигурации: [Docker в Amvera](https://docs.amvera.ru/applications/configuration/docker.html), [постоянное хранилище](https://docs.amvera.ru/applications/storage.html), [SQLite](https://docs.amvera.ru/databases/sqlite.html). Для веб-БД выбран DELETE journal: он не требует общего WAL shared-memory на сетевом томе. Фактическое развёртывание требует аккаунта и проекта Amvera; репозиторий подготовлен к нему, но сам по себе не создаёт облачный ресурс.

## Архитектура и сохранение правил

- `src/Planer.Core` скопирован без изменений из десктопного Planer, коммит `08c53b6`. В нём все повторы, перенос недели, привычки, история, платежи, финансовые ограничения и уведомления.
- `src/Planer.Data/SqlitePlannerStore.cs` сохранён для исходных тестов. Web использует только `WebDatabase` и `UserPlannerStore`: отдельную схему со столбцом `owner_id REFERENCES users(id)` во всех 12 таблицах планера, включая метаданные и отметки. Первичный ключ — `(owner_id,id)`. Любые чтение, upsert и удаление ограничены владельцем.
- `src/PlannerWeb` — MVC-контроллеры, модели форм, серверные Razor views, CSS и JavaScript без внешних CDN или frontend framework. Владелец берётся только из подписанной cookie, его нельзя передать запросом. Доступ требует авторизации; изменения требуют antiforgery token.
- `PlannerService` сериализует весь цикл загрузки/команды/сохранения, включая материализацию повторов, чтобы конкурентные вкладки не теряли изменения. Записи сохраняются транзакционно.
- Часовой пояс явно задан: даты не зависят от UTC хостинга. Новая неделя согласуется при обращении; открытый браузер проверяет смену дня раз в минуту.

Веб-версия начинает с отдельной пустой БД. Личная десктопная БД не читается и не изменяется. Попытка открыть её как веб-БД отклоняется. Синхронизация и импорт личных данных не добавлены.

Windows tray, автозапуск, COM и окно поверх других приложений относятся к ОС. В браузере стрелка открывает такой же экран текущего дня внутри сайта. Уведомления используют прежние правила Core, отображаются в открытой вкладке и ведут к дню/неделе/привычкам. Доставка при закрытом браузере не реализована. Для узких экранов сохранена исходная раскладка с горизонтальной прокруткой; отдельный день и формы помещаются на телефон.

## Проверки

```sh
dotnet build PlannerWeb.sln -c Release -warnaserror
dotnet run --project tests/Planer.Tests -c Release
dotnet run --project tests/PlannerWeb.Tests -c Release
dotnet publish src/PlannerWeb -c Release -o artifacts/publish
node scripts/verify-http.mjs
```

Node.js 24 нужен только для HTTP-проверок. Скрипт сам поднимает опубликованное приложение на loopback с одноразовой БД, проверяет регистрацию, вход, CSRF, чужие ID, HTML encoding, все экраны и сохранение, затем останавливает свой процесс и удаляет тестовые данные. Можно передать адрес уже запущенного **тестового** экземпляра.

В `tests/Planer.Tests` — 70 исходных сценариев; в `tests/PlannerWeb.Tests` — 37 проверок пользователей, владельцев, сохранения и конкурентных запросов. В HTTP suite — 41 проверка. GitHub Actions повторяет проверки на Linux, собирает Docker-образ, повторяет HTTP suite в Production, заменяет контейнер с постоянным томом и проверяет сохранность БД/ключей сессий по SHA256.

Рендер и взаимодействия дополнительно проверяются в скрытом браузере с отдельной QA-базой. Десктопный планер для этого не запускается. Исходные требования и дизайн находятся в [docs/desktop-requirements.md](docs/desktop-requirements.md); особенности веб-переноса описаны выше.
